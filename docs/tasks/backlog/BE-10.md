# Add Chat Reset Endpoint

Status: Completed on 2026-06-10.

## Summary

Create a backend endpoint that starts a new chat for the current anonymous session by clearing only the local session-to-conversation mapping.

The endpoint must not reset or replace the application session. It should remove the current session's row from `chat_conversations` so the next `POST /api/chat` request creates a new OpenAI conversation through the existing conversation resolution flow.

## Goal

When the shopper taps "new chat" in the frontend, the visible chat history should be cleared and the next message should start a fresh OpenAI conversation, while keeping the same anonymous backend session.

## Endpoint

`POST /api/chat/reset`

## Requirements

### 1. Session-Based Reset

For each request:

1. Resolve the current application `session_id` from the existing backend session mechanism.
2. Delete the `chat_conversations` record for that `session_id`, if one exists.
3. Do not accept `conversation_id` from query parameters, request body, or headers.
4. Do not delete or replace the `sessions` record.
5. Do not clear or expire the session cookie.

### 2. No OpenAI Call During Reset

The reset endpoint must not call OpenAI.

A new OpenAI conversation should be created only when the user sends the next message through `POST /api/chat` and no local mapping exists for the current session.

### 3. Idempotent Behavior

The endpoint should be safe to call repeatedly.

If the current session has no `chat_conversations` row, the endpoint should still return a successful response.

### 4. Response Format

Return a successful response with no body:

`204 No Content`

If the implementation needs to return JSON for frontend consistency, the response may instead be:

```json
{
  "messages": []
}
```

The chosen response format must be covered by automated tests.

### 5. Security

- Reset ownership must be determined only by the server-side session.
- A user must not be able to reset another session's conversation.
- The endpoint must not expose OpenAI API keys, raw upstream details, or internal database details.
- Client-provided `conversation_id` values must be ignored if present.

### 6. Error Handling

Handle the following cases:

- Missing or invalid current application session.
- Database failure while deleting the `chat_conversations` record.

Expected behavior:

- Return `500` for internal session resolution or database errors.
- Log internal errors without exposing sensitive details to the frontend.

## Acceptance Criteria

- `POST /api/chat/reset` exists.
- The endpoint resolves the current application session using the existing anonymous session mechanism.
- The endpoint deletes only the current session's row from `chat_conversations`.
- The endpoint does not delete, replace, expire, or otherwise reset the application session.
- The endpoint does not clear or replace the `grocery_session` cookie.
- The endpoint does not call OpenAI.
- Calling the endpoint when no conversation mapping exists succeeds.
- Client-provided `conversation_id` values are ignored and cannot affect another session.
- After reset, `GET /api/chat/history` for the same session returns an empty message list.
- After reset, the next `POST /api/chat` creates and stores a new OpenAI conversation for the same session.
- Automated tests cover existing mapping deletion, idempotent reset without a mapping, session preservation, session isolation, ignored client-provided conversation IDs, and next-message conversation recreation.
